# Ledger Sentinel

Three-way settlement reconciliation with a deterministic core and a gated AI
exception classifier. Built for Razorpay AI Buildathon **Track 04 — AI Finance
Controller**.

> Three CSVs go in — the merchant's orders, Razorpay's settlement report, the
> bank statement. A reconciled ledger, a diagnosed exception list and an audit
> log come out. And here is the case designed to fool it.

## Headline numbers

Measured on **seed_B**, which is generated by a different RNG stream and is never
inspected while anything is tuned. Regenerate them yourself with `make metrics`.

| Metric | Value |
|---|---|
| **False-match rate** | **0.0%** — 0 of 56 matches wrong |
| Match rate | **70.0%** — 56 of 80 orders |
| Adversarial cases correctly escalated | **2 / 2** |
| Unresolved | 9 bank credits, each with a written reason |
| Unlogged decisions | **0** |

**False-match rate is quoted first, before the match rate, and that ordering is
the argument of this project.** Any reconciliation tool can reach whatever match
rate you ask of it by lowering its standard of evidence. The costs are not
symmetric: an unresolved exception costs a controller ten minutes, a false match
closes a discrepancy that was real and nobody ever looks at it again. So the
number that leads is the one that can only get worse when the system gets
greedier.

Full breakdown, per case, regenerated on every run: [`docs/metrics.md`](docs/metrics.md).

## Run it

```bash
make setup     # uv venv on Python 3.11 + install
make test      # 200 tests
make lint
make data      # regenerate both seed datasets; must produce no diff
make metrics   # deterministic layer on held-out seed_B
make ai        # the whole system, replaying the committed response cache
make demo      # Streamlit -- the one command a judge runs
make api       # FastAPI on :8000; /docs is interactive evidence
```

**No step above needs an API key or a network connection.** Recording the
response cache does; nothing else. The offline path is the default, not the
fallback.

Then interrogate the result rather than trusting it:

```bash
sqlite3 ledger.db "select rule, count(*) from matches group by rule"
sqlite3 ledger.db "select bank_txn_id, rule, reason from exceptions"
sqlite3 ledger.db "select seq, rule, decision, reason from audit where subject_id='BNK00031'"
```

## The problem

A merchant's order book, the gateway's settlement report and the bank statement
never agree, and the disagreements are mostly boring: a platform fee, GST on that
fee, a T+2 gap stretched by a weekend, a refund netted inside a payout, several
settlements leaving as one consolidated credit. Existing tools report a match
rate and drop the residual on a human.

The hard part is not the arithmetic. It is that **some of the residual is
genuinely undecidable, and a tool that cannot tell the difference between "hard"
and "impossible" will resolve the impossible ones confidently.**

## How it works

```
orders.csv   settlements.csv   bank.csv
         \         |          /
        [ingest — strict pydantic, bad rows raise]
                   |
        [SQLite: orders settlements bank matches exceptions audit runs]
                   |
        [deterministic matcher]  ── matched, with the rule that fired
                   |
        unidentified credits, each carrying its candidate rows
                   |
        [exception classifier — LLM + 3 tools]
                   |
        [resolution gate]  confidence >= tau -> auto-resolve, else escalate
                   |
        [audit log] <- every decision, every rule, every reason
                   |
        [metrics]  false-match rate first
```

### A match requires an identifier

This is the thesis. **Amount agreement alone never closes a match, because
amounts collide.** Only a shared UTR opens one; the amount and the value date are
then used as *confirmation*, and a disagreement in either raises an exception
instead of a match. That single rule is why the false-match rate can be a
headline number rather than an aspiration.

Rules, in order:

| Rule | Outcome |
|---|---|
| `utr_exact` | UTR resolves to a payout whose net equals the credit exactly, inside the date window → **match** |
| `utr_within_rounding` | as above, off by ≤ 2 paise → **match**, drift recorded |
| `utr_amount_mismatch` | UTR matches, amount does not → **exception** |
| `utr_date_outside_window` | UTR matches, credit is dated outside the settlement window → **exception** |
| `utr_already_claimed` | a reference that matches twice has stopped identifying → **exception** |
| `unknown_utr` | reference on the statement, on no settlement row → **exception** |
| `no_identifier` | consolidated payout with nothing to join on → **exception**, handed to the classifier |

### Where AI is deliberately not used

Ingestion. Fee and GST arithmetic. The settlement calendar. Deterministic
matching. Subset-sum enumeration. Threshold gating. **The model classifies and
explains; it never computes money**, and every figure it is shown was computed by
the same functions the deterministic layer uses, so the two cannot disagree about
arithmetic.

### The gate does not trust confidence

Stated confidence is a self-report, and self-reports fail exactly where this
system must not: an amount collision *looks easy*, because the arithmetic closes
perfectly. So confidence is the **last** check, not the first. Before it:

1. **The arithmetic is re-verified** — the rows the model claims are re-summed
   against the credit using the matcher's own money functions. A right case with
   the wrong rows is not booked.
2. **Ambiguity vetoes any confidence** — if the tool trace holds two complete
   settlement batches that each explain the credit exactly and share no rows,
   nothing auto-resolves it. This is derived from evidence the model saw, not
   from its opinion of itself, so it holds even when the model misdiagnoses the
   case entirely. `tests/test_ai_layer.py` drives exactly that: a deliberately
   wrong diagnosis at confidence 1.0, still refused.
3. **Named adversarial cases never auto-resolve**, whatever the confidence.

*The plan named Claude for this layer; the build ships against OpenAI, which was
the key available. A dependency swap, not a design change — the classifier sits
behind a backend interface and neither the tools, the gate nor the metrics know
which vendor answered.*

### The matcher will not run subset-sum

A consolidated credit *could* be explained by some combination of settlement
rows, and enumerating those combinations is deterministic arithmetic — it lives
in `src/tools.py` for the classifier to call. But **deciding what to do when two
disjoint combinations both explain a credit exactly is a judgement**, and putting
it in the matcher would mean the matcher silently picking one. It would raise the
match rate and it would be the most expensive bug this system could ship.

That situation is not hypothetical; it is case 10, below.

## The dataset

Synthetic, generated, and published — `data/generator.py` is committed so a
reader can audit the difficulty of the data rather than take the match rate on
trust. Two independent seeds: **seed_A** tunes, **seed_B** reports. They share a
shape and no identifiers. Regenerating either is byte-identical, asserted in CI.

80 orders · 83 settlement rows · 65 bank lines · 65 ground-truth records, every
row claimed by exactly one.

| Case | Name | Resolved by | Units | Orders |
|---:|---|---|---:|---:|
| 1 | Clean match | deterministic | 18 | 18 |
| 2 | Fee and GST deducted | deterministic | 22 | 22 |
| 3 | Settlement timing gap | deterministic | 10 | 10 |
| 4 | Batched payout | tool | 4 | 12 |
| 5 | Refund netted into batch | ai | 3 | 6 |
| 8 | Paise rounding drift | deterministic | 6 | 6 |
| 10 | Amount collision | **escalate** | 2 | 6 |

Cases 6, 7, 9 and 11 are defined in `src/cases.py` and dormant. Turning one on is
a builder plus an entry in `ACTIVE_CASES` — not a redesign.

### Why 30% of it has nothing to join on

Every settlement row carries a UTR and so does every single NEFT credit, which
would have made this whole problem a SQL join. Rather than crippling the data by
deleting references, the generator models a real condition: **single NEFT credits
carry the UTR in the narration; consolidated payouts arrive over a different rail
with a generic narration and no reference at all.** No evidence is deleted — a
statement format that never carried it is modelled.

That is the honest difficulty knob, and it is also the boundary between the two
layers: 56 orders (70%) sit behind an identified credit and are deterministic; 24
orders sit behind consolidated credits and go to the classifier. The 70% is a
property of the dataset, not a tuned result — it is identical on both seeds.

### Case 10, the one designed to fool it

Three settlements sit in one window where `net(a) + net(b) == net(c)` exactly, and
the bank shows a single consolidated credit for that figure. Reading it as `c` and
reading it as `a + b` are both arithmetically perfect. Only one is true — it is
`a + b`; `c` was paid on a credit that falls outside this statement export, an
ordinary partial download.

Nothing in the data decides it. `c` is not on hold, not late, not flagged, and
sits in the same settlement window with the same `settled_at`. The credit has no
UTR to join on. **Confidence here is the failure; escalation is the only correct
output**, and the gate refuses to auto-resolve this case regardless of what
confidence the model claims.

Four tests in `tests/test_unit_dataset.py::TestCollisionIsGenuinelyAmbiguous`
prove the trap is genuinely set — a single row explains the credit exactly, a
disjoint pair also does, and no field distinguishes them. If a future change makes
case 10 solvable, those tests fail on purpose.

## Assumptions, and one deliberate deviation

Isolated in `config.py` so a reader can change one number and re-run `make
metrics`.

| Rule | Value | Status |
|---|---|---|
| Settlement lag | T+2 **working** days from capture | [verified] [Razorpay settlement FAQs](https://razorpay.com/docs/payments/settlements/faqs/) |
| GST | 18%, on the gateway's fee, not the transaction value | [verified] [Razorpay](https://razorpay.com/blog/international-payment-gateway-cost-india) |
| Platform fee | 200 bps on cards, netbanking, wallets | [verified] [Razorpay pricing](https://razorpay.com/pricing/) |
| Platform fee on UPI | **0 bps** | **[deviation]** — see below |
| Bank holidays | a representative subset | [assumed] — production reads the RBI calendar |

**The UPI deviation, stated in the open.** Razorpay's published pricing is 2% +
GST across *all* modes including UPI, because that 2% is Razorpay's platform fee
and not interchange; the NPCI zero-MDR mandate removes the interchange on
person-to-merchant UPI and RuPay debit, not an aggregator's own fee. We price UPI
at zero anyway, because the dataset needs one path where the bank credit equals
the order amount exactly — that is case 1, the control group. Without it every
case in the taxonomy involves fee arithmetic and the system can never demonstrate
a clean match. It is a modelling choice, it is wrong against the pricing page,
and it is better to say so here than to let a reader discover it.

## Scope

**In:** one merchant · three sources · one settlement cycle · an 11-case taxonomy
with 7 active · false-match rate · calibrated auto-resolution · an exception
report · a thin demo UI.

**Out:** multi-merchant · live Razorpay APIs · real money movement · marketplace
settlements · GST filing · anything past a demo dashboard.

**The forecast layer is cut.** The original plan paired this loop with a
payout-timing forecaster that would beat a naive T+2 baseline. It is not built and
it is not half-built — under a 72-hour track, one measured loop is worth more than
two gestured-at ones. It is issue #1 on the "with two more weeks" list along with
cases 6/7/9/11, multi-merchant, and live test-mode API ingestion.

**Scale.** At 10k records the subset-sum tool needs candidate windowing (by date
±3 days and method) and the matcher moves to indexed SQL. At 1M, batch the
classifier and move to Postgres. Not built; stated.

## Layout

```
config.py                every rate, window and threshold; nothing in src/ hardcodes one
src/cases.py             the 11-case taxonomy — the contract everything shares
src/money.py  dates.py   integer-paise fee/GST, T+2 business-day calendar
src/schema.py ingest.py  typed models; malformed rows raise, naming the line
src/db.py                SQLite — inspectable live in front of a judge
src/matcher.py           the deterministic layer, a pure function of the dataset
src/audit.py             one row per decision; zero unlogged decisions is asserted
src/pipeline.py          the one orchestration shared by CLI, API and tests
src/metrics.py           scoring; the only module allowed to read truth.json
src/tools.py             the three tools; subset_sum returns EVERY solution
src/llm.py               one call, two backends, a committed response cache
src/classifier.py        the tool-use loop; the prompt carries no answer key
src/gate.py              what may be booked without a human — confidence checked last
src/api.py  src/app.py   FastAPI and the Streamlit demo
data/generator.py        the dataset, with its ground truth, published
docs/                    GENERATED by make metrics — never hand-edited
```

Every number in every document here is emitted by code. CI runs `make data` and
`make metrics` and fails the build if a committed document has drifted from what
the code produces — because a document that disagrees with the system is not
documentation, it is a claim nobody re-checked.
